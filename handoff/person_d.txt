0. THE PRODUCT, IN ONE PARAGRAPH (so your decisions have a reason)
================================================================================
TestScope computes what a code change did to a test suite — not just which tests to
run. Given a diff, a test inventory and a repository, it answers four questions: which
tests must run, which are now STALE (they assert behaviour the change removed), which
became NEWLY RELEVANT (hidden behavioural coupling that no import graph shows), and
what has NO test at all. Every claim it makes is mechanically re-checked against the
repository before it counts. The measured reduction (about 90%) is the demo; the
product is the two questions no existing tool answers: which of my tests are now lying
to me, and which of my new behaviours has no test.

You own the difference between a demo and a product: the numbers, and the HONESTY of
the numbers. You are the last line of defence against an overclaim — and the first
person who would benefit from one, which is why you must be the most willing person on
the team to publish a zero.

  M4  Every published number must be reproducible by ONE command, and you must have

We report recall on a change whose ground truth WE EXECUTED, we state the DIRECTION of

5. THE ABLATION — does the AI layer earn its cost?
================================================================================
The system has a property that makes this trivial to run: a model layer that is
unavailable, wrong or hostile can only ever ADD tests, never remove them. So with the
model layer disabled, the selection must equal the deterministic baseline EXACTLY.

  model_layer = disabled -> selection == baseline (41 with the hero excluded)
  model_layer = enabled  -> selection == baseline ∪ verified additions (47)
  delta                  = recall(enabled) - recall(disabled)
  cost                   = coins_spent / max(1, delta_tests)

ASSERT the disabled run equals the baseline BYTE FOR BYTE. That assertion is what makes
the comparison meaningful; without it you are comparing a number to a bug.

PUBLISH THE RESULT EVEN IF IT IS ZERO. A measured zero is a finding and it is fully
defensible: "on this change, the semantic layer found nothing the symbolic layer
missed." If it is non-zero, the semantic catch IS the delta. Either way you have an
honest number. Write it as "the model layer contributed X additional true positives for
Y coins on this change" — never as a success rate on a sample of one.

================================================================================
A1. WHY THE ORACLE IS A LOWER BOUND, AND WHAT THAT COSTS US
================================================================================
The oracle decides that a test was affected if its OUTCOME CHANGED between the two
revisions. That is a sound way to detect a difference and it is cheap, but it has a
one-directional limitation: a test can be genuinely affected and still pass under both
revisions (for example, if it asserts a superset of the changed behaviour, or if the
changed path is not exercised by the inputs it happens to use). Therefore:
    the oracle's changed set  ⊆  the truly affected set
It is a LOWER BOUND. Consequences you must state wherever recall appears:
    - recall is measured in ONE direction only; over-selection is invisible to it, so a
      high recall does NOT mean we are tight, only that we did not miss what we could
      observe;
    - we never report precision from it, and never a completeness guarantee;
    - an empty `missed` list means "we missed nothing the instrument could see", which is
      a weaker and more honest sentence than "we missed nothing".
Underlying this is a theorem, not an implementation detail: deciding whether a change
alters the behaviour of a specific test is undecidable in general (Rice's theorem). So
NO tool — and no model — can guarantee completeness. What we can offer instead is
monotone soundness (the model layer can only ADD to the selection, never remove from
it, so its failure degrades to the baseline) plus a measured recall with its direction
disclosed. Both are checkable; the guarantee is not.

================================================================================
A2. PINS vs SPECIFIES, AND WHY CORRECTNESS IS NOT OURS TO CLAIM
================================================================================
Determining the EXPECTED output of a test is the oracle problem, and tooling does not
solve it. So the system separates two guarantees and never blurs them:
    PINS       the test will detect FUTURE changes to this behaviour. Mechanical, and
               proved by the G3 gate: an assertion must fire against the previous
               revision and the test must pass repeatedly against the current one.
               This says NOTHING about whether the CURRENT change was correct.
    SPECIFIES  the assertion encodes INTENDED behaviour, anchored to a specification
               artefact (a docstring, README, PR or issue text, a reproducer). Only as
               good as that artefact, and it exists only when the repository actually
               wrote its intent down.
Where no intent artefact exists, the honest sentence is "this behaviour is now pinned",
never "this behaviour is correct". Blurring the two manufactures exactly the dishonest
signal the field warns about: a suite that looks like it proves something it does not.
There is a second reason to be strict here. Generated tests frequently encode the ACTUAL
behaviour of the new code rather than the INTENDED behaviour, which converts bugs into
passing tests. That is why the acceptance criterion is "an assertion fires before the
change and passes after", not "coverage increased" — and why the authoring role is
deliberately denied sight of the post-change implementation.
