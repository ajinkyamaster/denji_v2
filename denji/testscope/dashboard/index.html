      Two honest caveats. LDRA does point at changed code that no test covers, so that column is not unique here. And newer tooling does rewrite stale tests when a published API schema changes; this report works from the diff itself and needs no schema, which is the difference — not the rewriting.

      How the report is put together

      Most of the work needs no guesswork and no reading — it is computed. Only two steps involve interpretation, and one needs a decision from you.

      1. computedRead the diff and the test inventory
      2. computedRun the suite on both commits to get the real breaks
      3. computedFollow imports from the changed code
      4. readLook for other code sharing the changed format
      5. checkedOpen every cited line and confirm the conclusion holds
      6. youChoose which uncovered behaviour to write tests for
      7. readWrite those tests, one file per behaviour
      8. computedProve each new test fails before the change and passes after
      9. computedWrite this report
